## 1. AI時代のGo開発2026: 爆速開発のためのガードレール

### 1-1. package by feature と internal / linter の役割

このセッションで強調されていたのは、「AIがコードを大量に生成しても、依存関係が崩れずに保守できる形にする」ことです。

Go で実現する典型的な形は次の 2 つです。

- `internal` で外部からのアクセスを制限する
- linter / analyzer で依存の向きや層の境界をチェックする

#### `internal` の意味

`internal` は、親ディレクトリ配下のパッケージだけが import できるルールです。

例:

- `myapp/internal/domain` は `myapp` 配下からだけ import できる
- `myapp/cmd/app` からは import できる
- `github.com/other-user/otherapp` からは import できない

これにより、以下のような「外部に見せたくない境界」を守れます。

- ある層の実装を外部に露出させたくない
- 依存関係の向きを固定したい
- モジュール分割した設計を壊しにくくしたい

#### package by feature の考え方

「utils に雑多に集める」よりも、機能ごとにまとまりを分ける方が、AI が生成したコードでも追いやすいです。

たとえば、次のような構成です。

- `feature/user/`
- `feature/order/`
- `feature/payment/`

それぞれの feature 配下に、必要な model / usecase / repository などを寄せます。

この形にすると、

- 依存の向きが自然にまとまる
- AI に対しても "この feature だけを触る" という意図が伝わりやすい
- レイヤーの境界が見えやすい

#### linter / analyzer の役割

`internal` だけでは完全ではありません。`internal` で守れるのは import ルールですが、
「どの層からどの層を呼んで良いか」まで厳密に規定するには linter や analyzer が必要です。

たとえば、

- `handler` から `repository` を直接呼ぶのを禁止する
- `usecase` から `cmd` のロジックを呼ばない
- `domain` から外部ライブラリに依存し過ぎない

といったルールを CI で守ると、AI 生成コードでも設計が崩れづらくなります。

### 1-2. fuzzing test とは何か

fuzzing は、手で作ったテストケースだけでは発見しにくい入力を自動で生成して、
クラッシュや不正な振る舞いを探すテスト手法です。

Go では以下のような形で書けます。

```go
func FuzzParseUser(f *testing.F) {
    f.Add("alice")
    f.Add("")

    f.Fuzz(func(t *testing.T, s string) {
        _ = ParseUser(s)
    })
}
```

#### 普通のテストとの違い

通常のテストは "想定した入力" を書きます。

- `"alice"` を入れたら OK
- `""` を入れたら error

一方 fuzzing は、

- たくさんの文字列を自動で生成
- 予期しない状態を探す
- パニックや不正なメモリアクセスにつながる入力を見つける

という点が違います。

#### 何に効くか

fuzzing は、特に次のような箇所に有効です。

- 文字列パース
- バイナリや JSON のデコード
- 正規表現やルーティング
- 変換処理

AI 生成コードでは「今回は想定していなかった入力」を通しやすいので、
fuzzing は "安全性を高めるための補助テスト" として有用です。

### 1-3. Mutation Testing とは何か

Mutation Testing は、テスト対象のコードを意図的に壊してから、
そのテストが失敗するかどうかを確認する手法です。

たとえば、次のような変更を入れます。

- `if x > 0` を `if x >= 0` に変える
- `return err` を削る
- 条件を反転する
- 1 行を消す

そして、

- そのテストが失敗すれば、テストがその振る舞いを検出できている
- 失敗しなければ、テストが弱い可能性がある

という判断をします。

#### なぜ必要か

通常のテストは「今のコードが通るか」を見るだけです。
しかし Mutation Testing は「コードが少し変わったらテストが拾えるか」を見るため、
テストの弱さをあぶり出せます。

実務で言うと、

- `if` の分岐が見逃されていないか
- `error` を返す経路をテストしているか
- `nil` や境界値のテストが足りているか

を確認しやすくなります。

#### ただし万能ではない

Mutation Testing は有効ですが、実行時間が増えたり、
多くの変異を作るとコストが上がります。

そのため、

- 100% を目指すのではなく
- 重要な分岐や危険な箇所だけを狙う

という使い方が現実的です。

### 1-4. AI時代のGo開発でのまとめ

このセッションで大事なのは、AI による高速な開発と、
品質を守るための境界の両立です。

- `internal` と linter で依存関係を制限する
- fuzzing で入力の想定外を拾う
- mutation testing でテストの弱さを検査する

この 3 つを組み合わせると、AI が生成したコードでも
"壊れにくい設計" と "壊れやすいテスト" を見分けやすくなります。

## 2. モジュラモノリスにおける internal の境界

このセッションのポイントは、"単一リポジトリの中で、依存関係の境界を明示する" ことです。

#### 何が嬉しいか

- 外部公開したくない実装を隠せる
- feature 間の依存を制限できる
- 変更の影響範囲を絞りやすい

#### 典型的な使い方

- `internal/domain` : ルールやモデル
- `internal/usecase` : ビジネスロジック
- `internal/repository` : DB や外部依存の実装

そして、上位レイヤーから下位レイヤーへだけ依存させる設計にすると、
見通しが良くなります。

## 3. Go から学ぶ GC の仕組みと Green Tea GC

このセッションの要点は、Go の GC が "今の Go でどう動いているか" を理解し、
次世代の GC へどうつながるかを掴むことです。

### 3-1. まず理解したいこと

Go の GC は、

- 参照されているオブジェクトを生存と判断する
- 参照されていないオブジェクトを回収する
- ヒープ上のメモリを再利用する

という仕組みで動きます。

### 3-2. サーバー環境と Wasm 環境の違い

#### サーバー環境

- GC はバックグラウンドで動くことがある
- アプリの実行と並行して回収が進む
- スループット重視の設計になっている

#### Wasm 環境

- ブラウザは基本的にシングルスレッド
- GC が走ると UI の実行が止まる可能性がある
- `GOMAXPROCS=1` で動く前提が強い
- `time.Sleep` や長い計算が UI を止めやすい

つまり、Wasm では "GC の停止時間" を意識することが非常に重要です。

### 3-3. Green Tea GC の位置づけ

Green Tea GC は、現行 Go の GC の代替候補として語られることのある次世代的な方向性です。

資料の趣旨としては、

- 現在の Go GC を理解する
- その上で、より低遅延やより良い最適化を目指す仕組みがある
- その可能性と注意点を知る

という点にあります。

実務で見ると、

- まだ現行の標準 GC を前提に設計することが多い
- ただし GC の特性を理解しておくと、
  大きなメモリを持つアプリや Wasm での挙動を読み解きやすくなる

ということです。

### 3-4. 実務で気にしたいこと

- 大きなオブジェクトを避ける
- 不要な割り当てを減らす
- ループや短命オブジェクトを意識する
- Wasm では UI と GC の干渉に注意する

## 4. まとめ

今回の「わからん」箇所を整理すると、次のような理解になります。

- **fuzzing** は手動テストでは拾えない入力を自動で探す仕組み
- **Mutation Testing** はテストの弱さを確認する仕組み
- **internal** は Go の依存関係境界を守る仕組み
- **GC** は Go のメモリ管理の中心で、Wasm では UI 停止を意識する必要がある

必要なら次に、

1. Go の `internal` を使ったサンプル構成
2. `go test -fuzz` の実践例
3. Mutation Testing のツール比較

まで掘り下げることもできます。
