このファイルは、当日のメモで「🤷‍♂️」になっていた箇所を、登壇資料・公開ページの情報をもとに整理した解説です。

## 1. TypeScriptの「型」をAIのスキルに昇華させてみた件について

このセッションの主題は、「TypeScript の型を、単なる静的チェックのための仕組みとしてではなく、AI に渡すスキル設計の材料として使う」ことです。話の中心は、AI に対して「何ができるか」「何を入力として受け取れるか」「どの形で返すか」を、型から読み取れるようにすることです。

### 1-1. 文字列とリテラルの使い分け

`string` と `"foo"` の違いは、AI にとってはとても大きいです。

- `string` は「任意の文字列」なので、AI は実際に何が来るかをあまり絞り込めません。
- `"foo"` のようなリテラル型は「この値だけが許可される」ので、AI はその選択肢を確定できます。

たとえば、API の `method` が `"GET" | "POST"` なら、AI はその範囲でしか選ばないように誘導できます。一方で `string` だと、`"DELETE"` や `"PATCH"` もあり得ると判断してしまいます。

この違いは、AI の「予測精度」に直結します。型が狭いほど、AI は動作やデータの形を正確に想像しやすくなります。

### 1-2. 型ガードなしのアサーションが危険な理由

TypeScript では `as SomeType` のような型アサーションを使うと、コンパイラに「この型だと信じる」と伝えられます。しかし、それは **型チェックを自分で捨てる** 行為です。

AI に対しても同じことが起きます。たとえば、AI が `result` を `User` と見なして使ってしまうと、実際の `result` の構造が違っていても、型の上では通ってしまいます。

その結果、

- 実行時エラー
- 不正なデータの流出
- 想定外の分岐

が起きやすくなります。つまり、型アサーションは「型を信頼する」ための手段ではなく、**その分だけ安全性を自分で放棄すること** だと理解するとよいです。

### 1-3. 判別可能なユニオンと `never` で完全性を検証する

判別可能なユニオンは、複数の分岐を「必ずどれか 1 つになる」形で表す手法です。典型例は `status` のような識別子を持つオブジェクトです。

```ts
type Success = { type: 'success'; data: string }
type Failure = { type: 'failure'; error: string }
type Result = Success | Failure
```

この形にしておくと、条件分岐の網羅性をコンパイラにチェックさせることができます。

```ts
function handle(result: Result) {
  switch (result.type) {
    case 'success':
      return result.data
    case 'failure':
      return result.error
    default:
      const _exhaustive: never = result
      return _exhaustive
  }
}
```

ここで `default` に `never` を置くのは、「ここに到達してはいけない」ことを表しています。もし新しい分岐を追加したのに `switch` を更新し忘れると、コンパイラがエラーを出します。

これは AI にとっても重要です。AI が生成したコードに新しいケースが足りないと、タイプレベルで検知できるからです。

### 1-4. Mapped Types による DRY な型設計

Mapped Types は、既存の型から別の型を機械的に生成する仕組みです。たとえば、

- `User` の各プロパティを `readonly` にした型
- `Optional<User>` のような型
- `Pick` / `Omit` で派生する型

が簡単に作れます。

AI の文脈では、**同じ変換ルールを何度も手書きしない** ための手段として使えます。たとえば API のレスポンス型と UI 側の表示型が似ている場合、Mapped Types を使って差分だけを上書きする形にすると、AI にとっても意図が読みやすくなります。

### 1-5. RORO パターン

RORO は「Receive an Object, Return an Object」という意味で、関数の引数や返り値を **オブジェクト 1 つ** にまとめるパターンです。

```ts
function createUser({ name, email }: { name: string; email: string }) {
  return { id: '1', name, email }
}
```

このパターンの利点は、

- 引数の追加・削除がしやすい
- 名前付きで呼べるので可読性が高い
- AI が関数の入力を理解しやすい

という点です。AI が「何を渡せばいいか」を解釈する際、引数が単発の `string` や `number` だと曖昧になりがちですが、オブジェクトにまとめると意味が明確になります。

### 1-6. narrowing による型の絞り込み

`narrowing` は、条件分岐や `in` / `typeof` / `instanceof` などを使って、型を絞り込む操作です。たとえば、

- `string | undefined` から `string` に絞る
- `Animal | Human` から `Human` に絞る

というように、実際の分岐ごとに型を安全に絞り込みます。

AI の文脈では、**型の中にある不確実性を減らす** ための基本テクニックです。より絞り込めると、AI に提示される情報が正確になり、生成結果のズレも減ります。

### 1-7. ブランド型で構造体を区別する

ブランド型は、構造が同じでも意味が違う型を区別するための手法です。

```ts
type UserId = string & { readonly __brand: 'UserId' }
type OrderId = string & { readonly __brand: 'OrderId' }
```

`UserId` と `OrderId` はどちらも `string` ですが、型としては別物です。これにより、

- `UserId` を `OrderId` に誤って渡す
- `email` を `userId` のように扱う

といったミスをコンパイル時に防げます。

AI にとっても、「この値は何を表す値か」を明示するための重要な手がかりになります。文字列のままだと意味が曖昧でも、ブランド型を付けると意味が固定されます。

### 1-8. このセッションのまとめ

このセッションで押さえておきたいのは、

- 型は **AI にとっての仕様書** になる
- 文字列よりリテラル、広い型より狭い型のほうが AI に優しい
- `never` / 判別可能なユニオン / narrowing / ブランド型は、AI 生成コードの安全性を支える

という点です。「型を書く」こと自体が、AI に提示する設計情報の量を増やすという意識が重要です。

## 2. TypeScriptだけでAIエージェントを作る ― フロント・エージェント・インフラのフルスタック実践

このセッションの要点は、**TypeScript だけで AI エージェントのフルスタックを組み上げる** ということです。公開ページの説明では、

- Claude Agent SDK を使ったエージェント構築
- AgentCore SDK を使ったサーバー層
- React/Vite を使ったフロントエンド
- AWS CDK を使ったインフラ定義

を、ひとつの TypeScript ベースの開発体験で扱うことが話題になっていました。

### 2-1. なぜ TypeScript だけで完結するのか

Python で AI エージェントを作るケースが多いことは事実ですが、TypeScript だけで完結できると、次のような利点があります。

- フロント・バック・インフラの型を統一できる
- 同じ言語で UI / API / IaC を扱える
- 生成したコードやツール定義に型が付く
- 既存の TypeScript 開発者の学習コストが低い

特に AI エージェント開発では、ツール定義や JSON 仕様をたくさん扱います。ここで TypeScript の型があると、**「どのツールが何を受け取り、何を返すか」** をコード上で固定しやすくなります。

### 2-2. 何が実務的に効くか

実務で見ると、TypeScript だけで AI エージェントを組むと、次のようなことがやりやすくなります。

- エージェントの入力・出力を型で管理する
- フロントでの UI 状態とサーバー側の変換を同じ型で扱う
- 生成するツールや API の定義を再利用しやすくする
- デプロイ周りも TypeScript で統一できる

つまり、**AI の「思考ロジック」だけでなく、周辺の実行基盤まで一貫して設計できる** のがこのセッションの価値です。

### 2-3. ここでの学び

このセッションを読むと、

- AI エージェント開発を Python に寄せる必然性はない
- TypeScript は API / UI / インフラを横断する「統一言語」として十分使える
- 重要なのは「AI の意思決定をどこまで型で固定するか」

ということがわかります。

## 3. TanStack Start の createServerFn で作る、型が通る API

このセッションの資料では、**「型が通ること」と「境界が設計されていること」は別物** だと強調されています。ここがメモの肝です。

### 3-1. `createServerFn` の役割

`createServerFn` は、クライアントから呼べるサーバー処理の入口です。実際の資料では、

- `inputValidator` で入力を検証する
- handler で実際の処理を行う
- `createServerFn` から返すデータを明示的に定義する

という形が示されています。

### 3-2. 何が壊れやすいか

資料では、`handler` に業務ロジック・DBアクセス・バリデーション・認可・通知などを詰め込む設計が壊れやすいとされています。

壊れやすい理由は次のとおりです。

- handler が肥大化する
- serverFn が「処理の境界」ではなく「業務ロジックの本体」になる
- 返すべきデータの範囲が曖昧になる
- クライアントが DB 由来の型に依存しやすくなる

この状態では、型は通っていても、実際の API 設計としては脆いままです。

### 3-3. 薄くするという考え方

資料が強調していたのは、`serverFn` を **薄い境界** にするという考え方です。

具体的には、

- `serverFn` は入力検証と、UseCase への委譲だけをやる
- 実際の業務ロジックは `UseCase` 側に置く
- `serverFn` は API の入口としての責務に留める

という構成です。

### 3-4. 出力も Schema 化する

ここが実務でかなり重要です。単に `return row` のように返すと、

- スキーマと型のズレ
- 不要な内部フィールドの露出
- クライアント向けの契約が不明確

になる可能性があります。

そのため、出力も Zod のような Schema で明示し、`parse` で整形する形がよいとされています。

つまり、**入力も出力も「型安全だけでなく、契約として定義する」** のがポイントです。

### 3-5. loader と serverFn の役割分担

資料では、`loader` と `serverFn` を明確に分けて説明しています。

- `loader` は Route に必要なデータを引き渡す場所
- `serverFn` は「実際にサーバー側で処理を実行する」境界

`loader` に DB へのアクセスや認可ロジックを置くと、責務が混ざりやすいので避けるべきです。`loader` は「表示に必要な最小限の情報を引き出す」ための場所に寄せるのがよいという理解です。

### 3-6. Next.js の `useSWR` との比較

このセッションを理解するための比較として、Next.js の `useSWR` を考えるとわかりやすいです。

- `useSWR` は **クライアント側でデータ取得を行う** ための仕組み
- `createServerFn` は **サーバー処理をクライアントから呼べるようにする** ための仕組み

つまり、`useSWR` は「データを取る」ことに寄せた API ですが、`createServerFn` は「サーバー処理そのものを関数として公開する」点が違います。

`createServerFn` を使うと、

- クライアント側から RPC 的に呼べる
- サーバー側の処理を薄い入口に閉じ込められる
- 返り値や入力の契約を明示しやすい

という設計がしやすくなります。

## 4. TanStack Router の型定義を読み解く

このセッションの公開ページの説明からわかるのは、**TanStack Router はルート定義そのものを型情報の起点にしている** という点です。通常のルーターでは、型は実装に後付けでつくることが多いですが、TanStack Router では、ルート定義を記述した時点でルーティングの型が生成される、という設計です。

### 4-1. 何が「型の起点」なのか

ルート定義にパスや検索パラメータや loader の返り値が含まれていると、そこから TypeScript の型が派生します。つまり、

- ルートの URL
- パスパラメータ
- 検索パラメータ
- loader の戻り値

がすべて型として伝播していきます。

そのため、

- 存在しないパスへ遷移しようとする
- パラメータの型が違う
- loader の戻り値の型と利用側がズレる

といった問題を、コンパイル時に見つけやすくなります。

### 4-2. ルート定義が型を生むという意味

この考え方は、単に「型を定義する」ことではなく、**ルーティングの設計そのものを型の源泉にする** ことです。

たとえば、URL の構造が変われば、それに依存する型も変わります。つまり、ルートの変更をするだけで、関連する代入や呼び出し側の型も追随します。

実際の開発では、こうした型の伝播を使うと、

- ルーティングの実装ミスを減らせる
- ルートごとの引数仕様が明確になる
- loader や navigation の API を型安全に扱える

というメリットがあります。

### 4-3. このセッションの要点

このセッションが示していたのは、

- ルート定義は「URL の宣言」ではなく「型の定義」でもある
- 型をどう設計するかが、ルーティングの安全性に直結する
- ルーティングを型で縛ると、実装より先に仕様を固定しやすい

という点です。

## 5. Zod v4 Codec でスキーマに型変換を埋め込む REST API 設計 👍

このセッションの公開ページの説明では、REST API の設計において、

- フロントエンドでは `Dayjs` のような型で扱いたい
- API では ISO 文字列を返したい
- その変換を毎回手書きしたくない

という課題が掲げられていました。そこに **Zod v4 Codec** が登場します。

### 5-1. Codec とは何か

Codec は、単なるバリデーションではなく、**変換の定義をスキーマに含める** ための仕組みです。ひとことで言うと、

- 入力を受け取るときに変換する
- 出力するときに変換する
- その変換ロジックをスキーマと一緒に管理する

という考え方です。

### 5-2. 何が便利なのか

従来の REST API 設計では、

- API のレスポンス型
- フロントで使う型
- DB の型

が別々に存在しやすく、変換レイヤーを手で書く必要がありました。Codec を使うと、

- バリデーション
- 型変換
- 既存の Zod のスキーマ設計

をひとつの流れで扱えるようになります。

これは、

- フロントとバックの型のズレを減らす
- 変換ロジックが散らばらない
- 変換を仕様として固定できる

という意味で、実務上かなり強いです。

### 5-3. Hono + Drizzle を使う場合のイメージ

このセッションでは Hono と Drizzle を例としていました。ここでのポイントは、

- DB から取得した値
- API に返す値
- フロントで使う値

を、すべて小さな変換ルールでつなげるということです。

たとえば、

- DB には `timestamp` として保存
- API には ISO 文字列で返す
- フロントでは `Date` や `Dayjs` で扱う

というように、**外部に見せる形と内部の保存形を分ける** ための設計に向いています。

### 5-4. このセッションで得られる考え方

このセッションの本質は、

- 型変換を「別レイヤーの手作業」にしない
- スキーマに変換の意図を埋め込む
- API 設計を型とデータ変換の両方から守る

という点です。

## 6. まとめ

この Day1 の `🤷‍♂️` は、すべて **「型・境界・変換の扱い方」** に関わる話だったと整理できます。

- **型を AI のスキル設計に使う** という視点
- **serverFn の境界を薄く保つ** という設計
- **ルート定義そのものを型の源泉にする** というアプローチ
- **Zod の Codec で変換をスキーマに埋め込む** という実装パターン

これらは、AI 生成コードや TypeScript の実装品質を上げるための共通テーマとしてつながっています。

「型が通る」ことだけでは十分ではなく、**どこで型の責務を持ち、どこで変換し、どこで境界を作るか** を設計できるようになることが、今の TypeScript の肝だと理解できます。
