## 1. Hono RPC と Drizzle ORM で実現する、AI にも優しい TypeScript ファーストな開発

このセッションの本題は、**型定義と実装を同じ TypeScript の世界で完結させる** ことです。Hono RPC と Drizzle を組み合わせると、バックエンドの API 定義、DB スキーマ、クライアント呼び出しの型がひとつの言語で揃い、AI エージェントがコード生成・修正をしやすい形になります。

### 1-1. Aurora Data API について

メモで触れられていた **Aurora Data API** は、AWS Aurora に対して HTTP ベースの API を介してアクセスする仕組みです。通常の RDS/Aurora への接続では、DB へのネットワーク経路を開ける必要がありますが、Data API ならその前提を簡略化できます。

#### 何が便利か

- **VPC やセキュリティグループの設計を意識しなくてよい**
  - 直接 TCP 接続を使わず、AWS 側の API 経由でアクセスできます。
  - サーバーレスやエッジ寄りの実装で、接続先の制約を減らせます。
- **外部からのアクセスを安全に扱いやすい**
  - DB に直接到達する必要がないため、接続経路の開放を最小限にできます。
- **Lambda やサーバーレス環境との相性がよい**
  - 常時起動しない実行環境でも利用しやすい点が魅力です。

#### どんなときに使うか

- **直接接続の管理が複雑な構成**
  - VPC 内部の DB にアクセスする際に、Lambda や Edge からの経路設計を簡略化したいとき。
- **DB へのアクセスを API 経由で抽象化したい**
  - インフラの接続詳細をアプリ側に持ち込まず、AWS 側に寄せたいとき。
- **"外部から直接アクセスできる" という意味**
  - これは "DB への TCP 接続を自分で開かなくてもアクセスできる" という意味で、VPC 越えの接続設計を単純化できることを示しています。

#### 使わなかった理由の読み方

メモの「使わなかった」という記述は、**Aurora Data API の価値がないという意味ではなく、今回の実装では別の方針を取った** という意味に近いです。たとえば次のような理由が考えられます。

- 既存の DB 接続設計を維持したかった
- 性能・料金の観点で直接接続のほうが合理的だった
- 既存の ORM / クエリ実装との整合性を優先した
- アプリの実行環境を想定したとき、Data API では足りない要件があった

#### 料金と性能の注意点

Aurora Data API は便利ですが、**リクエスト単位の料金が発生する** ため、負荷が高いケースでは従来の接続方式のほうが有利なことがあります。つまり、

- **小規模・サーバーレス寄りの利用** では効果が大きい
- **高頻度の DB アクセス** では、接続方式の選定を見直す価値がある

という理解が必要です。

### 1-2. PGlite について

メモで「PGlite を入れたが、何が嬉しいのかわからなかった」とあった箇所は、**PGlite の用途が「本番 DB の代替」ではなく「開発・テスト・実行環境の補助」** にあることを理解すると納得しやすいです。

#### PGlite とは

PGlite は、**PostgreSQL を WebAssembly に移植した実装** です。ブラウザや Node.js の中で PostgreSQL 相当の機能を使えるようにしたものです。

#### 何が嬉しいか

- **ローカル開発が軽くなる**
  - Docker や別サービスを立てずに、アプリと同じ Node プロセス内で DB を使えることがあります。
- **テストがしやすい**
  - テストごとに初期化しやすく、CI でも扱いやすいです。
- **ブラウザ内で DB を使える**
  - たとえばフロント側でデータを近い形で試したいときに有効です。
- **TypeScript 環境と相性がよい**
  - TypeScript で DB スキーマやクエリを扱っているケースでは、実行環境の差異を感じにくいです。

#### どんな用途に向くか

- **ローカル開発やサンプルアプリ**
- **E2E やユニットテストの補助 DB**
- **ブラウザ内でのデモやプロトタイプ**
- **オフラインや軽量な実行環境**

#### どんな点に注意するか

PGlite は便利ですが、**本番のメイン DB として使う用途には向かないことが多い** です。理由は次のとおりです。

- そのまま大規模な並行アクセスや高負荷を想定しにくい
- 本番の運用・監視・バックアップの設計と別物になりやすい
- PostgreSQL の完全互換までは想定しない場合がある

つまり、**PGlite は「本番代替」ではなく「開発と実行の柔軟性を上げるツール」** という理解が大事です。

### 1-3. この talk での意味づけ

Hono RPC と Drizzle を使うと、

- **型定義の単一化**
- **コード生成に頼らない API 体験**
- **AI エージェントが扱いやすい入力・出力の規約**

が揃いやすくなります。ここで注目したいのは、"型が通る" ことと、"AI にとって理解しやすい契約がある" ことが別物ではなく、同じ方向に寄っているという点です。

### 1-4. まとめ

このセッションの要点をまとめると、次のようになります。

- **Aurora Data API** は、DB への直接接続を避けたい場合に有効な抽象化レイヤーである
- **PGlite** は、PostgreSQL 相当の軽量実行環境として、開発・テスト・プロトタイプに向く
- **Hono RPC + Drizzle** は、TypeScript だけで API と DB を扱う設計の骨格を作りやすい
- **AI にとって理解しやすいのは、型だけでなく、実装境界が明確な設計** である
