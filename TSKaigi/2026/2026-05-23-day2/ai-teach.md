このファイルは、当日のメモで「🤷‍♂️」になっていた箇所を、登壇資料の公開情報と一般的な実装文脈をもとに整理した解説です。

## 1. Hono RPC と Drizzle ORM で実現する、AI にも優しい TypeScript ファーストな開発

このセッションの本題は、**型定義と実装を同じ TypeScript の世界で完結させる** ことです。Hono RPC と Drizzle を組み合わせると、バックエンドの API 定義、DB スキーマ、クライアント呼び出しの型がひとつの言語で揃い、AI エージェントがコード生成・修正をしやすい形になります。

### 1-1. Aurora Data API について

メモで触れられていた **Aurora Data API** は、AWS Aurora に対して HTTP ベースの API を介してアクセスする仕組みです。通常の RDS/Aurora への接続では、DB へのネットワーク経路を開ける必要がありますが、Data API ならその前提を簡略化できます。

#### 何が便利か

- **VPC やセキュリティグループの設計を意識しなくてよい**
  - 直接 TCP 接続を使わず、AWS 側の API 経由でアクセスできます。
  - サーバーレスやエッジ寄りの実装で、接続先の制約を減らせます。
- **外部からのアクセスを安全に扱いやすい**
  - DB に直接到達する必要がないため、接続経路の開放を最小限にできます。
- **Lambda やサーバーレス環境との相性がよい**
  - 常時起動しない実行環境でも利用しやすい点が魅力です。

#### どんなときに使うか

- **直接接続の管理が複雑な構成**
  - VPC 内部の DB にアクセスする際に、Lambda や Edge からの経路設計を簡略化したいとき。
- **DB へのアクセスを API 経由で抽象化したい**
  - インフラの接続詳細をアプリ側に持ち込まず、AWS 側に寄せたいとき。
- **"外部から直接アクセスできる" という意味**
  - これは "DB への TCP 接続を自分で開かなくてもアクセスできる" という意味で、VPC 越えの接続設計を単純化できることを示しています。

#### 使わなかった理由の読み方

メモの「使わなかった」という記述は、**Aurora Data API の価値がないという意味ではなく、今回の実装では別の方針を取った** という意味に近いです。たとえば次のような理由が考えられます。

- 既存の DB 接続設計を維持したかった
- 性能・料金の観点で直接接続のほうが合理的だった
- 既存の ORM / クエリ実装との整合性を優先した
- アプリの実行環境を想定したとき、Data API では足りない要件があった

#### 料金と性能の注意点

Aurora Data API は便利ですが、**リクエスト単位の料金が発生する** ため、負荷が高いケースでは従来の接続方式のほうが有利なことがあります。つまり、

- **小規模・サーバーレス寄りの利用** では効果が大きい
- **高頻度の DB アクセス** では、接続方式の選定を見直す価値がある

という理解が必要です。

### 1-2. PGlite について

メモで「PGlite を入れたが、何が嬉しいのかわからなかった」とあった箇所は、**PGlite の用途が「本番 DB の代替」ではなく「開発・テスト・実行環境の補助」** にあることを理解すると納得しやすいです。

#### PGlite とは

PGlite は、**PostgreSQL を WebAssembly に移植した実装** です。ブラウザや Node.js の中で PostgreSQL 相当の機能を使えるようにしたものです。

#### 何が嬉しいか

- **ローカル開発が軽くなる**
  - Docker や別サービスを立てずに、アプリと同じ Node プロセス内で DB を使えることがあります。
- **テストがしやすい**
  - テストごとに初期化しやすく、CI でも扱いやすいです。
- **ブラウザ内で DB を使える**
  - たとえばフロント側でデータを近い形で試したいときに有効です。
- **TypeScript 環境と相性がよい**
  - TypeScript で DB スキーマやクエリを扱っているケースでは、実行環境の差異を感じにくいです。

#### どんな用途に向くか

- **ローカル開発やサンプルアプリ**
- **E2E やユニットテストの補助 DB**
- **ブラウザ内でのデモやプロトタイプ**
- **オフラインや軽量な実行環境**

#### どんな点に注意するか

PGlite は便利ですが、**本番のメイン DB として使う用途には向かないことが多い** です。理由は次のとおりです。

- そのまま大規模な並行アクセスや高負荷を想定しにくい
- 本番の運用・監視・バックアップの設計と別物になりやすい
- PostgreSQL の完全互換までは想定しない場合がある

つまり、**PGlite は「本番代替」ではなく「開発と実行の柔軟性を上げるツール」** という理解が大事です。

### 1-3. この talk での意味づけ

Hono RPC と Drizzle を使うと、

- **型定義の単一化**
- **コード生成に頼らない API 体験**
- **AI エージェントが扱いやすい入力・出力の規約**

が揃いやすくなります。ここで注目したいのは、"型が通る" ことと、"AI にとって理解しやすい契約がある" ことが別物ではなく、同じ方向に寄っているという点です。

### 1-4. まとめ

このセッションの要点をまとめると、次のようになります。

- **Aurora Data API** は、DB への直接接続を避けたい場合に有効な抽象化レイヤーである
- **PGlite** は、PostgreSQL 相当の軽量実行環境として、開発・テスト・プロトタイプに向く
- **Hono RPC + Drizzle** は、TypeScript だけで API と DB を扱う設計の骨格を作りやすい
- **AI にとって理解しやすいのは、型だけでなく、実装境界が明確な設計** である

## 2. LLM 時代のリファクタリング戦略：AI エージェントによる段階的・安全な TS 移行方法

このセッションの肝は、**「型を当てる」ことと「移行を安全に進める」ことは別物** だという点です。大規模な JavaScript プロジェクトを TypeScript に移行する場合、単にファイルを `.ts` に変えるだけでは、実際の品質や安全性は担保できません。

### 2-1. 何が難しいか

大規模フロントエンドの移行では、次のような複雑さが出ます。

- 既存の JavaScript の暗黙的な挙動が多い
- どのモジュールが外部依存として機能しているかが見えにくい
- 変更範囲が広く、誤った変換で挙動を壊しやすい
- 型の追加だけでは「修正の意味」が足りない

このため、AI による移行は「大量のコードを置き換える」だけではなく、**どこまでを安全に型付けし、どこから手作業で確認するか** を設計することが重要です。

### 2-2. 段階的移行の考え方

この talk が強調していたのは、**段階的に進める** という姿勢です。単発の一括移行では、リグレッションのリスクが高くなります。そこで、

- まずは型の導入対象を限定する
- 変換対象の境界を明確にする
- AI が安全に触れる範囲を段階的に広げる

という形で進めるのがポイントです。

### 2-3. OpenAPI 生成クライアントと AI の連携

話の中で、OpenAPI から生成したクライアント SDK と AI エージェントをどう組み合わせるかが示されていました。ここでの意図は、AI に「API の呼び出し形」を型付きで渡し、AI がその契約に沿ってコードを生成しやすくすることです。

つまり、

- API の境界が型で固定されている
- AI はその型に基づいて実装を組み立てる
- 手動で扱うべき箇所だけを人間がレビューする

という流れです。これにより、AI は「何を呼ぶべきか」「どの型で受け渡すべきか」を理解しやすくなります。

### 2-4. 「意味のある型」を浸透させる

この talk の最も重要なポイントは、**単に `any` や `unknown` を置き換えるだけでは意味がない** という点です。型を追加する際に、

- どのドメインの概念か
- どの層の責務か
- どの API との境界か

を意識して設計する必要があります。

そうして初めて、AI は「この型が何を表すのか」を理解して、適切な修正や生成を行いやすくなります。

### 2-5. 実務的な意味

このセッションから得られる実務上の学びは、

- **大規模移行は「型の導入」ではなく「移行戦略の設計」** である
- **AI は型と境界のある場所で真価を発揮する**
- **安全性は、段階的な制御とレビュー設計で確保する**

という点です。

## 3. Next.js × OpenAPI で型安全なデータ境界を設計するアーキテクチャ改善

このセッションでは、**フロントエンドとバックエンドの境界を、型で明示的に設計する** ことが語られていました。特に、OpenAPI を使ってスキーマ駆動開発を進める場合、型安全性を UI 側まで引き継ぐ設計が重要になります。

### 3-1. 何が問題だったか

従来の実装では、

- UI 層と BFF 層の境界があいまい
- フロント側で「どのデータを受け取るべきか」が明確でない
- OpenAPI の型安全性をフロントに十分に反映できていない

という状態がありました。

### 3-2. DAL を導入した意味

この talk の要点は、**Data Access Layer (DAL) を導入して、UI に渡すデータの型を明示化した** ことです。DAL を挟むことで、

- フロントエンドが直接バックエンドの実装詳細に依存しない
- UI に渡すデータの形を限定できる
- 型の責務が分かりやすくなる

というメリットがあります。

### 3-3. データ境界の効果

型安全なデータ境界を設けると、

- どの層が何を知っているべきかが明確になる
- API の変更が UI 側の型エラーとして現れる
- 変更の影響範囲を把握しやすくなる

という形で、開発の見通しが良くなります。

### 3-4. 何を学ぶべきか

このセッションから学ぶべきは、

- **OpenAPI のスキーマは「API の仕様」だけでなく、フロントの型設計の出発点** になりうる
- **境界層を挟むと、型安全性が単なるチェックではなく設計の仕組みになる**
- **UI に渡す型を明示することで、実装の責務分離が進む**

という点です。

## 4. TypeScript で Platform SDK を作る技術

このセッションの主題は、**プラットフォーム向け SDK を TypeScript で設計し、利用者に正確で使いやすい型を提供する** ということです。特に、SDK を使う側の開発体験を重視している点が特徴です。

### 4-1. ユーザー設定に応じた型の提供

SDK の利用者ごとに異なる設定がある場合、単一の型では足りません。そこで、

- ビルド済みのパッケージに後からユーザー固有の型情報を注入する
- 利用者ごとの設定に応じて、適切な型を提供する

という設計が話題になっていました。

この考え方は、**SDK の利用者の文脈を型に反映する** という意味で重要です。型が固定されすぎると、実際の利用環境との差が広がり、SDK の使い勝手が落ちます。

### 4-2. 実行環境を意識させないコード変換

SDK の実装では、ローカル実行とプラットフォーム実行の差異をユーザーに見せない工夫が必要です。つまり、

- ユーザーが実行環境の違いを意識しなくてよい
- 余計な設定やコードを増やさずに、同じ API を使える
- ローカルテストと実環境の挙動を揃える

という方向です。

### 4-3. AI フレンドリーな SDK

この talk では、AI が SDK を使って実装課題を解くことを評価するような観点も示されていました。つまり、SDK は単に人間向けの API ではなく、**AI が扱いやすい形で設計されるべき** という考え方です。

AI 向けに重要なのは、

- 使える API の境界が明確であること
- 入力と出力の型がきれいに定義されていること
- 余計な概念を増やさず、利用者が迷わないこと

です。

### 4-4. このセッションの要点

SDK 開発を通して得られる教訓は、

- **型は利用者ごとの文脈まで考慮して設計する**
- **実行環境の差異を隠蔽できる設計が重要**
- **AI 向けの使いやすさも、SDK の品質の一部になる**

という点です。

## 5. Polymorphic Components パターンで作る、型安全でセマンティックな UI コンポーネント

このセッションでは、**コンポーネントのレンダリング先を柔軟に選べる** ことと、**TypeScript の型でそれを安全に制御する** ことがテーマでした。

### 5-1. Polymorphic Components の狙い

Polymorphic Components は、

- ボタンやリンクのように、同じ UI ロジックを別の HTML 要素に割り当てられる
- `button` なのか `a` なのかで許容される属性が変わる
- その差分を型で安全に表現する

というパターンです。

### 5-2. 型安全性のポイント

このパターンの肝は、**選んだ要素に応じて属性の型が変わる** ことです。たとえば、

- `button` なら `type` 属性を受け取れる
- `a` なら `href` を受け取れる
- そのほかの要素では、別の属性集合が許容される

というように、コンポーネントの props を要素種別に応じて絞り込める点です。

### 5-3. デザインシステムでの意味

デザインシステムでは、見た目を統一しつつ HTML の意味論を保つ必要があります。Polymorphic Components を使うと、

- セマンティックな HTML を保ちやすい
- スタイルの再利用がしやすい
- 不適切な属性の混入を防げる

というメリットがあります。

### 5-4. このセッションの実務的な意義

この talk から得られる実務上の学びは、

- **型は UI の制約を表現するための道具** になりうる
- **コンポーネントの API を設計する際に、適切な HTML の意味を型で守れる**
- **再利用性の高い UI を TypeScript で安全に作れる**

という点です。
