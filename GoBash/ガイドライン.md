# ガイドライン

登壇資料「npm との違いを手がかりに Go の依存管理を理解したい」を作るための、疑問と実験のロードマップ。

## 進め方

1 つの疑問につき、この 4 ステップを繰り返す。

```text
1. 疑問を立てる        … 「Go を使っているだけだと理解できていないこと」を言語化する
2. コマンドで確認する  … 推測で書かない。必ず手元で実行して出力を採取する
3. 必要ならソースを読む … /usr/local/go/src/cmd/go/internal/... まで降りる
4. GoBash/ex-Go/question.md に追記する … 出力をそのまま貼り、図（テキスト）で流れを描く
```

書くときのルール:

- コマンドとその**実際の出力**を必ずセットで載せる
- 「Go はこうなっている」ではなく「こう確認したらこうだった」の順で書く
- 各疑問の最後に「次に湧く疑問」を 1 行書いて、次の疑問へ橋を架ける

## 第1段階: 外部依存を入れた瞬間に何が起きるか

### 疑問4: `go get` したら `go.sum` が突然生まれた。go.sum は誰がいつ作るのか？

```bash
cd GoBash/ex-Go

# 実行前の状態を記録
ls -la
cat go.mod

# 外部パッケージを追加
go get github.com/go-chi/chi/v5

# 実行後の差分を見る
ls -la
cat go.mod
cat go.sum
git diff
```

観測ポイント:

- `go.mod` に `require github.com/go-chi/chi/v5 vX.Y.Z` が増える
- `go.sum` が新規作成される（`go get` が副作用で作る。手で書くファイルではない）
- まだ `main.go` で import していないのに `require` される（`go get` はソースを見ない）
- この状態で `go mod tidy` を打つと require が消える → 疑問14 への伏線

### 疑問5: ダウンロードされた実体はどこにある？ なぜ `node_modules` のようにプロジェクト直下に来ないのか？

```bash
go env GOMODCACHE
/Users/shiraki_takuma/go/pkg/mod

ls $(go env GOMODCACHE)/github.com/go-chi
chi        chi@v1.5.5

ls $(go env GOMODCACHE)/github.com/go-chi/chi
v5@v5.3.2

# 展開済みソースを読む（実体はここ）
go list -f '{{.ImportPath}} {{.Dir}} {{.Module.Path}}@{{.Module.Version}}' github.com/go-chi/chi/v5
github.com/go-chi/chi/v5 /Users/shiraki_takuma/go/pkg/mod/github.com/go-chi/chi/v5@v5.3.2 github.com/go-chi/chi/v5@v5.3.2

# 書き込み権限を確認する（読み取り専用になっている）
ls -l $(go env GOMODCACHE)/github.com/go-chi/
total 0
drwxr-xr-x@  3 shiraki_takuma  staff   96 Sep 13 22:02 chi
dr-xr-xr-x@ 21 shiraki_takuma  staff  672 Sep 13 22:02 chi@v1.5.5
```

観測ポイント:

- 実体は**プロジェクト外のグローバルキャッシュ**にある → 全プロジェクトで共有される
- ディレクトリ名にバージョンが入る（`chi@v5.x.x`）ので複数バージョンが共存できる
- パーミッションが読み取り専用 → 「依存を書き換えられない」設計
- npm の `node_modules`（プロジェクトごとにコピー、書き換え可能、巨大）との対比ポイント

### 疑問6: そもそもどこから取ってきたのか？ `git clone` しているのか？

```bash
go env GOPROXY GOSUMDB GOPRIVATE GONOPROXY GONOSUMDB GOVCS
# GOPROXY='https://proxy.golang.org,direct'
# GOSUMDB='sum.golang.org'

# ダウンロードの内部動作を出力させる
go clean -modcache          # ※ 全プロジェクトのキャッシュが消える。実演直前だけにする
go mod download -x github.com/go-chi/chi/v5

# モジュールプロキシを直接叩いてみる（Go コマンドがやっているのと同じこと）
curl -s https://proxy.golang.org/github.com/go-chi/chi/v5/@v/list
curl -s https://proxy.golang.org/github.com/go-chi/chi/v5/@latest
curl -s https://proxy.golang.org/github.com/go-chi/chi/v5/@v/v5.0.12.info
curl -s https://proxy.golang.org/github.com/go-chi/chi/v5/@v/v5.0.12.mod

# キャッシュのダウンロード層を見る（.info / .mod / .zip / .ziphash が並ぶ）
ls $(go env GOMODCACHE)/cache/download/github.com/go-chi/chi/v5/@v/
```

観測ポイント:

- `git clone` ではなく **HTTP で zip を取得**している（`GOPROXY` 経由）
- `$GOMODCACHE/cache/download` に生データ、`$GOMODCACHE/<module>@<version>` に展開後が置かれる 2 層構造
- `GOPROXY` を `direct` にすると VCS 直アクセスに変わる → `GOPROXY=direct go mod download -x` で比較できる
- npm registry との対比（tarball を取る点は似ている／プロキシが immutable である点が違う）

## 第2段階: go.sum の正体（登壇の核心）

### 疑問7: go.sum の 1 モジュールに 2 行（`h1:` と `/go.mod h1:`）あるのはなぜ？

```bash
cat go.sum
grep chi go.sum
```

```text
github.com/go-chi/chi/v5 v5.x.x h1:...=          ← モジュールの zip（ソース全体）のハッシュ
github.com/go-chi/chi/v5 v5.x.x/go.mod h1:...=   ← そのモジュールの go.mod 単体のハッシュ
```

深掘り:

- `h1:` は dirhash。ファイル名とファイル内容の SHA-256 を並べたリストを、さらに SHA-256 したもの
- 実装: `/usr/local/go/src/golang.org/x/mod/sumdb/dirhash/hash.go`（`HashZip` / `Hash1`）
- なぜ `go.mod` 単体のハッシュが別にあるのか → 依存解決では **go.mod だけ先に読む**（ソース本体を落とさずグラフを構築する）から。疑問11・13 に繋がる

### 疑問8: go.sum を書き換えたらどうなる？（改ざん検証の実演）

```bash
# 正常時
go mod verify
# => all modules verified

# わざと壊す（1 文字書き換える）
cp go.sum go.sum.bak
sed -i '' 's/h1:a/h1:b/' go.sum
go clean -modcache
go build ./...
# => SECURITY ERROR / checksum mismatch が出る

# 戻す
mv go.sum.bak go.sum
```

観測ポイント:

- ビルドが**失敗する**（警告ではなく停止する）
- npm の `package-lock.json` は書き換えても `npm install` が通ってしまうケースがある、という対比
- 「go.sum は依存を固定するためではなく、取得物が改ざんされていないことを証明するためにある」

### 疑問9: go.sum は `package-lock.json` なのか？（ロック vs 検証）

```bash
# go.sum を消してもビルドは通るのか？
mv go.sum /tmp/go.sum.bak
go build ./...      # go.sum が再生成される。バージョンは変わらない
diff /tmp/go.sum.bak go.sum

# go.mod だけでバージョンが決まることを確認する
go list -m all
```

観測ポイント:

- **バージョンを決めているのは `go.mod`**、`go.sum` ではない → だから go.sum を消しても同じものが入る
- npm は `package.json` が `^1.2.3` のようなレンジなので、lock がないと解決結果が変わりうる
- オチ:「**go.mod は宣言、go.sum は証明**」

### 疑問10: そのハッシュの正しさは誰が保証している？（Checksum Database）

```bash
go env GOSUMDB GONOSUMDB GOPRIVATE
# GOSUMDB='sum.golang.org'

# checksum database を直接引く
curl -s https://sum.golang.org/lookup/github.com/go-chi/chi/v5@v5.0.12

# sumdb のキャッシュを見る
ls $(go env GOMODCACHE)/cache/download/sumdb/

# sumdb を無効にして取得した場合との差
GONOSUMDB=github.com/go-chi/* go get github.com/go-chi/chi/v5
GOFLAGS=-mod=mod GONOSUMCHECK=1 go mod download   # 参考: 挙動比較用
```

観測ポイント:

- `sum.golang.org` は追記のみの透明性ログ（Merkle Tree）。過去のハッシュを書き換えられない
- ローカルの `go.sum` に無いモジュールを初めて取るとき、Go は sumdb に問い合わせて照合する
- 社内モジュールは `GOPRIVATE` / `GONOSUMDB` で除外する、という実務の話に繋げられる

## 第3段階: バージョン解決（npm との対比の主戦場）

### 疑問11: 同じモジュールの違うバージョンを 2 つ要求したらどうなる？（MVS）

```bash
# 依存グラフ全体を出す
go mod graph
go mod graph | grep <module>

# 最終的に選ばれたバージョン一覧
go list -m all

# なぜそのバージョンなのかを問う
go mod why -m github.com/go-chi/chi/v5

# 更新候補を見る（自動では上がらないことを確認する）
go list -m -u all
```

観測ポイント:

- Go は要求された中の**最小で条件を満たすバージョン**を選ぶ（MVS: Minimal Version Selection）
- 解決は決定的。同じ go.mod なら誰がいつ実行しても同じ結果 → **lock が要らない理由**
- npm は最新に寄せる解決 + hoisting で、結果が実行時期や順序に依存する

### 疑問12: なぜ Go は lock なしで再現できるのか？

- `package.json` の `^1.2.3` = レンジ → 解決に自由度がある → lock で固定が必要
- `go.mod` の `v1.2.3` = 下限の宣言 + MVS = 解決に自由度がない → lock が不要
- 歴史: `dep` 時代には `Gopkg.lock` があった。なぜ捨てられたか（構成案の「論の必然」枠）

### 疑問13: `// indirect` は何か？ なぜ go.mod に間接依存まで書かれるのか

```bash
cat go.mod | grep indirect
go mod graph | head -30
go list -m -f '{{.Path}} {{.Version}} indirect={{.Indirect}}' all
```

観測ポイント:

- Go 1.17 の module graph pruning 以降、ビルドに必要な依存は indirect も含めてメインの go.mod に展開される
- 目的は「全依存の go.mod を読みに行かなくても解決できる」= 解決の高速化
- `GoBash/ex-Go/README.md` 冒頭のメモがここに対応する

### 疑問14: `go mod tidy` は何をしているのか？

```bash
cat go.mod
go mod tidy -v
git diff go.mod go.sum
```

観測ポイント:

- ソースの import を実際に走査して require を増減させる（`go get` は走査しない）
- go.sum からも不要なエントリが消える／必要なエントリが足される
- 疑問4 で「import していないのに require された」状態がここで解消される

## 第4段階: 余力があれば

| 疑問 | 確認コマンド |
| --- | --- |
| import path に `/v5` が入る理由（Semantic Import Versioning） | `go list -m github.com/go-chi/chi/v5` / v4 と v5 を同時に require してみる |

| モジュールキャッシュとビルドキャッシュの違い | `go env GOCACHE GOMODCACHE` / `go clean -cache` と `-modcache` の差 |
| GOPATH → dep → Go Modules の歴史 | `go help gopath` / dep の `Gopkg.lock` を資料で引用 |

### 注意

- `go clean -modcache` は**全プロジェクト共有のキャッシュ**を消す。再取得に時間がかかるので、実演の直前だけにする
- 登壇デモでネットワークに依存するコマンド（`go get` / `curl proxy.golang.org`）は、出力を事前にキャプチャしておく
- `go.sum` を壊す実験は必ずバックアップを取ってから行い、終わったら `git checkout go.sum` で戻す
